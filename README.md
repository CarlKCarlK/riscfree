# riscfree

ESP32-C3 firmware for the LuatOS Core Board. Rust places a fixed `u128` on the
stack in data RAM, passes its address to an assembly popcount, and reports the
returned `u8` over serial:

```text
popcount(0xd3a57c1902efb6489d306a17c2f5804b) = 61
popcount_swar(0xd3a57c1902efb6489d306a17c2f5804b) = 61
```

Each firmware build calls one of two routines:

| Routine | Source | Static instructions | Code size | Executed instructions |
| --- | --- | --- | --- | --- |
| `popcount128` (bit loop) | `src/popcount.S` | 14 | 56 bytes | 664 |
| `popcount128_swar` | `src/popcount_swar.S` | 28 | 112 bytes | 76 |

Both routines read four aligned 32-bit words and count their set bits. They
leave memory and callee-saved registers unchanged. The Rust harness supplies the
input, calls the selected routine, prints the result, and asserts that it equals
61. After the assertion passes, Rust idles indefinitely.

The SWAR routine was generated by Rust 1.91.0 at `opt-level = "s"` for
`riscv32imc` and then commented by hand. It is assembled with `.option norvc`,
so every instruction is a 32-bit word, and `zext.b` links as `andi a0, a1, 255`.

## Lean proof

Run `just prove` with Elan, Python 3, and GNU binutils installed. It checks
the Lean proofs, then builds each firmware variant and compares the linked bytes of the
routine it calls with the instruction words decoded by Sail: all 56 bytes of
`popcount128` and all 112 bytes of `popcount128_swar`. Lake uses the pinned
Pico FV and Sail dependencies in `lake-manifest.json` and Lean 4.28.0-rc1.

`popcount128SailCorrect` and `popcount128SwarSailCorrect` cover every 128-bit
input. Each states the exact number of Sail instructions until the return:
664 for the bit loop and 76 for SWAR (10 setup, 4 × 16 loop, and 2 return
instructions). Each also states that the routine returns to `ra` with the
population count of `inputBits` in `a0` and preserves byte memory. All registers
also keep their values except the PC, Sail's internal `nextPC`, and the registers
the routine writes: `a0` and `t0`–`t4` for the bit loop, and `a0`–`a7` and `t0`
for SWAR. Both theorems depend on exactly the same axioms, all of which come
from the Sail model and Lean's standard axioms. Neither proof uses `sorry`,
`native_decide`, or `bv_decide`.

`just prove` enforces this with two checks:

- `scripts/check_proof_sources.py` scans `proof/` (outside comments and
  strings) for shortcuts such as `sorry`, `native_decide`, `bv_decide`, new
  `axiom` declarations, `unsafe` code, `#exit`, and code that runs during
  elaboration.
- `scripts/AxiomAudit.lean` imports every module under `proof/` and collects
  the axioms the kernel recorded for all their declarations. It accepts only
  Lean's `propext`, `Classical.choice`, and `Quot.sound`, plus the 69 listed
  Sail extern stubs (floating-point, reservation, terminal, and entropy
  functions). Each stub must be declared in `LeanRV32D.RiscvExtras` and have a
  nonempty type, so assuming it cannot introduce a contradiction. Sail's Lean
  backend declares these externs as axioms, and they reach every theorem about
  `step` because `execute` covers every instruction.

Sail decodes each linked word through a pre-simplified decoder.
`proof/Riscfree/RV32/DecoderNormalForm.lean` runs `simp` once over Sail's
whole RV32 decoder applied to a symbolic word. The state is in machine mode
with landing pads disabled. The result is a kernel-checked definition,
`decodeMachineMode`, and an equation theorem. `decode_word` rewrites a
concrete word with that theorem and lets the kernel reduce the result, so
decoding needs no per-instruction lemmas. A new program writes its instruction
table (each word with the AST it should decode to) and calls `decode_table`
with the state facts. In a one-off experiment outside the build, with one word
per mnemonic, this decoded every base integer instruction and the `Zicsr`,
`Zifencei`, `Zicond`, and system instructions.
`proof/Riscfree/RV32/DecodeExamples.lean` checks stores, calls, `auipc`,
unsigned comparisons, shifts, and byte loads that no popcount routine uses.
Instructions gated by a `misa` bit, such as those of the M, A, and B
extensions, still read `misa` in the normal form. For those, `decode_word`
falls back to the earlier per-word `simp` with hand-picked Sail lemmas, which
today covers SWAR's `mul`.

The per-word SWAR identity is proved in the kernel. Each word is split into
eight nibbles. Every SWAR step either acts on each nibble separately or moves
whole nibbles without a carry, and the per-nibble facts are checked for all 16
values. `bv_decide` proves the same identity, but it would add
`Lean.ofReduceBool` and `Lean.trustCompiler` to the trusted base.

The files are:

- `proof/PopcountSpec.lean`: the mathematical specification shared by both proofs.
- `proof/Popcount.lean` and `proof/PopcountSwar.lean`: the application proofs.
  They contain the instruction table, register snapshot, one lemma per linked
  instruction, loop invariants, and the final theorem.
- `proof/Riscfree/RV32/`: reusable RV32 infrastructure. It provides register
  snapshots synchronized with the Sail state, a step lemma per opcode built on
  Pico FV's equivalence theorems, the platform premises, the pre-simplified
  decoder, and the `decode_word` and `decode_table` tactics.
- `proof/Riscfree/NormalForm.lean` and `proof/Riscfree/StateRun.lean`:
  infrastructure independent of RISC-V. The `normal_form` command simplifies a
  definition once and adds the result and its equation theorem through the
  kernel. The `StateRun` lemmas push a known `EStateM` state through binds and
  branches.
- `proof/Riscfree/Elf.lean`: the linked-byte check.

On a clean build, `lake build` spends about 15 minutes, once, simplifying the
decoder. After that, `Popcount` elaborates in about 60 seconds and
`PopcountSwar` in about 100, compared with 84 and 145 seconds when every word
went through `simp`. `just kernel-check` optionally replays every module under
`proof/` through Lean's `leanchecker`. It is not part of `just prove` and takes
about 6 minutes, one module at a time.

Each theorem's `entry` premise and `Platform` structure specify the starting
state and execution conditions. The code mapping supplies the linked halfwords
to Sail's instruction fetch. The four data words occupy naturally aligned,
readable RAM and agree with the little-endian input bytes. The hart runs in
machine mode with `MPRV` clear, the host interface and landing-pad checks
disabled, and a four-byte-aligned return address. The SWAR proof also assumes
that `misa.M` is set, because Sail decodes `mul` only when the M extension is
enabled. The model steps each instruction and commits the PC. Interrupt
delivery and hardware counters are outside that model. The proof trusts the
Rust harness and ESP32-C3 hardware.

## Firmware

Install the Rust target and flashing tool:

```bash
rustup target add riscv32imc-unknown-none-elf
cargo install espflash --locked
```

In WSL 2, attach the board with `hey attach-esp` if the global recipe is installed.

```bash
just check     # Type-check the firmware
just build     # Build release firmware
just run       # Build, flash, and open the serial monitor (bit loop)
just run swar  # Same, but call the SWAR routine in src/popcount_swar.S
just prove     # Check both proofs and both routines' linked bytes
just kernel-check  # Optional: replay every proof module with leanchecker
```
