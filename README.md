# riscfree

ESP32-C3 firmware for the LuatOS Core Board. Rust places a fixed `u128` on the
stack in data RAM, passes its address to an assembly popcount, and reports the
returned `u8` over serial:

```text
popcount(0xd3a57c1902efb6489d306a17c2f5804b) = 61
popcount_swar(0xd3a57c1902efb6489d306a17c2f5804b) = 61
```

Without the board, `just emulate` runs the same linked routines under QEMU
(see [Emulator](#emulator)).

Each firmware build calls one of two routines:

| Routine | Source | Static instructions | Code size | Executed instructions |
| --- | --- | --- | --- | --- |
| `popcount128` (bit loop) | `src/popcount.S` | 14 | 56 bytes | 664 |
| `popcount128_swar` | `src/popcount_swar.S` | 28 | 112 bytes | 76 |

Both routines read four aligned 32-bit words and count their set bits. They
leave memory and callee-saved registers unchanged. The Rust harness supplies the
input, calls the selected routine, prints the result, and asserts that it equals
61. After the assertion passes, Rust idles indefinitely.

The SWAR routine was generated by Rust 1.91.0 at `opt-level = "s"` for
`riscv32imc` and then commented by hand. It is assembled with `.option norvc`,
so every instruction is a 32-bit word, and `zext.b` links as `andi a0, a1, 255`.

## Lean proof

Run `just prove` with Elan, Python 3, and GNU binutils installed. It checks
the Lean proofs, then builds each firmware variant and compares the linked bytes of the
routine it calls with the instruction words decoded by Sail: all 56 bytes of
`popcount128`, all 112 bytes of `popcount128_swar`, all 120 bytes of
`raw_vec_u32_insert`, all 28 bytes of its calling shim, all 132 bytes of
`raw_vec_pair_insert`, all 92 bytes of `raw_vec_u32_remove`, and all 100 bytes
of `raw_vec_pair_remove`. It makes the same comparison for the QEMU harness,
and checks that the harness has no compressed instructions. Neither check
needs the board or QEMU. Lake uses the pinned
Pico FV and Sail dependencies in `lake-manifest.json` and Lean 4.28.0-rc1.

`popcount128SailCorrect` and `popcount128SwarSailCorrect` cover every 128-bit
input. Each states the exact number of Sail instructions until the return:
664 for the bit loop and 76 for SWAR (10 setup, 4 × 16 loop, and 2 return
instructions). Each also states that the routine returns to `ra` with the
population count of `inputBits` in `a0` and preserves byte memory. All registers
also keep their values except the PC, Sail's internal `nextPC`, and the registers
the routine writes: `a0` and `t0`–`t4` for the bit loop, and `a0`–`a7` and `t0`
for SWAR. Both theorems depend on exactly the same axioms, all of which come
from the Sail model and Lean's standard axioms. Neither proof uses `sorry`,
`native_decide`, or `bv_decide`.

`just prove` enforces this with three checks, then the linked-byte check:

- `scripts/check_proof_sources.py` scans `proof/` (outside comments and
  strings) for shortcuts such as `sorry`, `native_decide`, `bv_decide`, new
  `axiom` declarations, `unsafe` code, `#exit`, and code that runs during
  elaboration.
- `scripts/AxiomAudit.lean` imports every module under `proof/` and collects
  the axioms the kernel recorded for all their declarations. It accepts only
  Lean's `propext`, `Classical.choice`, and `Quot.sound`, plus the 69 listed
  Sail extern stubs (floating-point, reservation, terminal, and entropy
  functions). Each stub must be declared in `LeanRV32D.RiscvExtras` and have a
  nonempty type, so assuming it cannot introduce a contradiction. Sail's Lean
  backend declares these externs as axioms, and they reach every theorem about
  `step` because `execute` covers every instruction. It reads each audited
  module's own constant table. `--reference` additionally runs the original,
  much slower scan of the whole environment and fails unless both select the
  same declarations and reach the same axioms.
- `scripts/AxiomPaths.lean` (`just axiom-paths`) prints a shortest dependency
  chain to each axiom of `rawVecU32InsertSailCorrect`. It fails unless the
  instructions the routine executes reach only Lean's three axioms and four
  Sail stubs. [docs/rawvec-assurance.md](docs/rawvec-assurance.md) explains
  why none of the four affects this routine.
- `scripts/LinkedBytes.lean` compares each routine's linked bytes in every
  firmware and QEMU ELF with the instruction table its proof decodes. It also
  checks the shim offset and the QEMU harness's lack of compressed
  instructions. It runs in one Lean process and imports the proof modules, but
  no proof imports it, so editing it rebuilds no proof. The same run requires
  it to reject eight corrupted copies (one flipped bit in each of the six
  routines and the shim, and a set RVC flag) that `scripts/corrupt_elf.py` writes.

Sail decodes each linked word through a pre-simplified decoder.
`proof/Riscfree/RV32/DecoderNormalForm.lean` runs `simp` once over Sail's
whole RV32 decoder applied to a symbolic word. The state is in machine mode
with landing pads disabled. The result is a kernel-checked definition,
`decodeMachineMode`, and an equation theorem. `decode_word` rewrites a
concrete word with that theorem and lets the kernel reduce the result, so
decoding needs no per-instruction lemmas. A new program writes its instruction
table (each word with the AST it should decode to) and calls `decode_table`
with the state facts. In a one-off experiment outside the build, with one word
per mnemonic, this decoded every base integer instruction and the `Zicsr`,
`Zifencei`, `Zicond`, and system instructions.
`proof/Riscfree/RV32/DecodeExamples.lean` checks stores, calls, `auipc`,
unsigned comparisons, shifts, and byte loads that no popcount routine uses.
Instructions gated by a `misa` bit, such as those of the M, A, and B
extensions, still read `misa` in the normal form. For those, `decode_word`
falls back to the earlier per-word `simp` with hand-picked Sail lemmas, which
today covers SWAR's `mul`.

The per-word SWAR identity is proved in the kernel. Each word is split into
eight nibbles. Every SWAR step either acts on each nibble separately or moves
whole nibbles without a carry, and the per-nibble facts are checked for all 16
values. `bv_decide` proves the same identity, but it would add
`Lean.ofReduceBool` and `Lean.trustCompiler` to the trusted base.

The files are:

- `proof/PopcountSpec.lean`: the mathematical specification shared by both proofs.
- `proof/Popcount.lean` and `proof/PopcountSwar.lean`: the application proofs.
  They contain the instruction table, register snapshot, one lemma per linked
  instruction, loop invariants, and the final theorem.
- `proof/RawVec/Insert.lean`: what every element type shares: the
  specification of `RawVec<T>::insert`, its memory footprint, the copy-loop
  invariant, and the final memory. `proof/RawVec/Access.lean` states the memory
  and code-mapping premises any routine needs.
- `proof/RawVec.lean` and `proof/RawVec/Instructions.lean`: the `u32`
  instance: execution proof and 30-instruction table.
- `proof/RawVec/PairInsert.lean` and `proof/RawVec/PairInsert/Instructions.lean`:
  the same for `RawVec<Pair>` (eight-byte elements) and its 33 instructions.
  [docs/rawvec-pair-cost.md](docs/rawvec-pair-cost.md) records what the second
  instance cost.
- `proof/RawVec/Remove.lean`: the same shared layer for `RawVec<T>::remove`.
  `proof/RawVec/U32Remove.lean` and `proof/RawVec/PairRemove.lean`, with their
  `Instructions.lean` tables (23 and 25 instructions), instantiate it for `u32`
  and `Pair`. [docs/rawvec-remove-cost.md](docs/rawvec-remove-cost.md) records
  what removal cost on top of insertion.
- `proof/RawVec/Compatibility.lean`: the original `u32` definitions and
  theorem statements, from before the generic refactoring, derived from the
  current theorems.
- `proof/RawVec/Shim.lean`: the calling shim's instruction table and its
  composition with the routine.
- `proof/RawVec/Nonvacuity.lean`, `proof/RawVec/PairInsert/Nonvacuity.lean`,
  `proof/RawVec/U32Remove/Nonvacuity.lean`, and
  `proof/RawVec/PairRemove/Nonvacuity.lean`: concrete machines that satisfy
  every premise of the RawVec and shim theorems, one per execution path, built
  on the shared model in `proof/RawVec/Model.lean`.
- `proof/Riscfree/RV32/`: reusable RV32 infrastructure. It provides register
  snapshots synchronized with the Sail state, a step lemma per opcode built on
  Pico FV's equivalence theorems, the platform premises, the pre-simplified
  decoder, and the `decode_word` and `decode_table` tactics. `Fetch.lean`
  derives Sail's instruction fetch from machine mode, PMA, and the code bytes.
  `Model.lean` provides building blocks for concrete machines.
- `proof/Riscfree/NormalForm.lean` and `proof/Riscfree/StateRun.lean`:
  infrastructure independent of RISC-V. The `normal_form` command simplifies a
  definition once and adds the result and its equation theorem through the
  kernel. The `StateRun` lemmas push a known `EStateM` state through binds and
  branches.
- `proof/Riscfree/Elf.lean`: the ELF reading behind `scripts/LinkedBytes.lean`.

On a clean build, `lake build` spends about 15 minutes, once, simplifying the
decoder. After that, `Popcount` elaborates in about 60 seconds and
`PopcountSwar` in about 100, compared with 84 and 145 seconds when every word
went through `simp`. `just kernel-check` optionally replays every module under
`proof/` through Lean's kernel, one module at a time, with `leanchecker`'s
replay function (`scripts/KernelCheck.lean`), 16 modules in parallel by default
(`just kernel-check 8` for fewer). It is not part of `just prove` and takes
about 3 minutes.

With everything built, `just prove` takes about 110 seconds, mostly the axiom
checks. Editing an application theorem such as `proof/RawVec/PairInsert.lean`
rebuilds in about 13 seconds. Editing a table of step lemmas such as
`proof/RawVec/PairInsert/Instructions.lean`, or a module it imports, costs
about 80 seconds.

The decoder normal form is rebuilt only when
`proof/Riscfree/RV32/DecoderNormalForm.lean`, a module it imports
(`Riscfree.NormalForm`, `Riscfree.StateRun`, and `Riscfree.RV32.Effects`), the Lean toolchain, or
the pinned Lake packages change. Application proofs and the rest of
`proof/Riscfree/RV32/` do not invalidate it. To seed a new worktree, copy an
existing worktree's `.lake` directory with `cp -a` before the first
`lake build`. Lake checks each module's source and imports and rebuilds only
what differs, so a stale copy costs time but never yields an unchecked
module. Do not share `.lake` between worktrees with a symbolic link or hard
links, because a build in one would then overwrite the other's files.

Each theorem's `entry` premise and `Platform` structure specify the starting
state and execution conditions. The code mapping supplies the linked halfwords
to Sail's instruction fetch. The four data words occupy naturally aligned,
readable RAM and agree with the little-endian input bytes. The hart runs in
machine mode with `MPRV` clear, the host interface and landing-pad checks
disabled, and a four-byte-aligned return address. The SWAR proof also assumes
that `misa.M` is set, because Sail decodes `mul` only when the M extension is
enabled. The model steps each instruction and commits the PC. Interrupt
delivery and hardware counters are outside that model. The proof trusts the
Rust harness and ESP32-C3 hardware.

### Bounded-vector insertion

`rawVecU32InsertSailCorrect` describes the final contents of every live slot
after inserting a `u32`. It also specifies the new length, unchanged pointer
and capacity, and unchanged memory outside the length word and the written
suffix. Error checks take precedence in this order: invalid length, invalid
index, full capacity. Every rejected call preserves all byte memory.

The theorem gives 14 instructions for append and `18 + 6m` for insertion
before a suffix of `m > 0` elements. Invalid length, invalid index, and full
capacity take 5, 6, and 7 instructions respectively.

`rawVecPairInsertSailCorrect` (and its `InMachineMode` form) states the same
guarantee for `RawVec<Pair>`, where `Pair` is two `u32` words passed in `a2`
and `a3`. Each slot's two words hold the result pair (`PairAt`). It takes 15
instructions for append and `19 + 8m` for insertion before `m > 0` pairs, and
it also writes `t0` and `t1`. Both theorems instantiate one generic
specification and loop invariant (`proof/RawVec/Insert.lean`).

The model needs a mapped, word-aligned code image and return address.
Because the routine stores to memory, `Environment` states the platform
premise, including the code mapping, for every memory that agrees with the
original on the routine's 120 code bytes.
`rawVecU32InsertSailCorrectInMachineMode` gives the same guarantee without
that premise. It replaces `Environment` with `MachineMode` (the machine-mode
registers and the return address) and `CodeImage` (the code bytes in memory
that the PMA lets Sail fetch). `proof/Riscfree/RV32/Fetch.lean` derives each
fetch from Sail's semantics, and `Environment.ofMachine` derives the old
premise from the new ones.
Rejected calls require only the two readable length and capacity words.
Successful calls additionally require a readable backing pointer, the
initialized live prefix, read permission for shifted source words, and write
permission for the changed slots and length word. The header and the accessed
buffer addresses must fit in the RV32 address space, the live buffer and header
must be disjoint, and every write must be disjoint from the code. No permission
is required for spare slots after the new length.

`proof/RawVec/Nonvacuity.lean` proves that these premises can all hold. It
builds a concrete machine for each of the five execution paths and applies the
theorem to it. [docs/rawvec-assurance.md](docs/rawvec-assurance.md) describes
the model.

The ESP32-C3 demo calls the routine through the seven-instruction shim in
`examples/raw_vec_call.S`. It gives the routine a four-byte-aligned return
address even when the surrounding firmware uses compressed instructions.
`proof/RawVec/Shim.lean` proves the shim and the routine together, using the
shim's linked words. `just prove` checks the shim's 28 linked bytes and that the
shim's `call` reaches the routine 0xbc bytes later. `build.rs` assembles the
shims into their own object and links it directly before the routines, so that
offset does not change when the demo's own code does. The pair routine has an
identical shim, which is not proved.

- `callRawVecU32InsertSailAtReturn` covers the first six instructions for any
  caller. After `call.count + 6` instructions, the shim stands at its `ret`
  with the routine's status in `a0`, and with `ra`, `sp`, and every register
  outside `a0`–`a7` restored. Memory matches the routine's result, except
  that the stack word below `sp` holds the saved `ra`.
- `callRawVecU32InsertSailCorrect` adds the `ret` when the caller's return
  address is word-aligned.

The pinned Sail configuration does not support compressed instructions, so it
faults on a jump to an address with bit 1 set. In the demo, two of the five
`RawVec<u32>` calls return to such an address. For those calls, the final
`ret` is trusted to the hardware. [docs/rawvec-assurance.md](docs/rawvec-assurance.md) lists
everything still trusted about the Rust caller.

### Bounded-vector removal

`rawVecU32RemoveSailCorrect` and `rawVecPairRemoveSailCorrect` (each with an
`InMachineMode` form) verify one generic `RawVec<T>::remove`
([research/vec-ffi/linked/raw_vec_remove.rs](research/vec-ffi/linked/raw_vec_remove.rs)).
Called with the header in `a0` and an index in `a1`, it removes the element at
the index, moves each later element one slot toward the front with a forward
copy loop, and decrements the length. The removed element is not returned.
The theorems describe every slot of the new live prefix, the new length, the
unchanged pointer and capacity, and unchanged memory outside the length word
and the slots from the index to the new length. The vacated last slot keeps
its old value. An invalid length (`length > capacity`, status 3) is checked
before an invalid index (`index >= length`, status 2, including any index of
an empty vector), and both leave all memory unchanged. Both theorems also state
that every register except the PC, `nextPC`, and `a0`–`a4` (`a0`–`a5` for
`Pair`) keeps its value.

Removing the last element takes 9 instructions. Removing before `m > 0` later
elements takes `15 + 4m` for `u32` and `15 + 6m` for `Pair`. The rejections take
5 and 6. A successful call needs read permission for the elements after the
index, write permission for the slots from the index to the new length, and
those slots disjoint from the header and the code. Rejected calls need only
the length and capacity words. Each routine's nonvacuity module proves the
premises satisfiable on all four paths, plus an empty vector.

The demo calls each removal routine through a shim in
`examples/raw_vec_remove_call.S`, a copy of the insertion shim. These shims
are not proved. `build.rs` links the removal routines and shims after the
insertion objects, so the verified shim's call offset does not move.

## Firmware

Install the Rust target and flashing tool:

```bash
rustup target add riscv32imc-unknown-none-elf riscv32im-unknown-none-elf
cargo install espflash --locked
```

The RawVec and SortedMap demo also needs Elan, Python 3, and GNU binutils
for the pre-flash checks.

In WSL 2, attach the board with `hey attach-esp` if the global recipe is installed.

```bash
just check     # Type-check the firmware
just build     # Build release firmware
just run       # Build, flash, and open the serial monitor (bit loop)
just run swar  # Same, but call the SWAR routine in src/popcount_swar.S
just run-raw-vec   # Verify RawVec and SortedMap in the built ELF, then flash and monitor
just prove         # Check all proofs and every verified routine's linked bytes
just kernel-check  # Optional: replay every proof module through the kernel
```

## Emulator

Without an ESP32-C3, run the same linked routines under QEMU's generic
RV32 `virt` board:

```bash
rustup target add riscv32im-unknown-none-elf
sudo apt install qemu-system-misc   # Debian, Ubuntu, and WSL 2

just emulate          # Bit-loop popcount
just emulate swar     # SWAR popcount
just emulate-raw-vec  # RawVec<u32> and RawVec<Pair> insertion and removal, every outcome
```

The harness in `emulator/` runs in machine mode, prints over the board's UART,
and exits through QEMU's test device. It shares its test cases in
`src/cases/` with the firmware. It is compiled entirely without compressed
instructions, so its return addresses are word-aligned. It calls the four
RawVec routines directly, without the shims, and every call meets the theorems' word-aligned return-address premise,
including for the final `ret`. `just prove` checks that the routines' bytes in
the QEMU harness are the ones Lean verified. The emulator is a convenience for
reproducing the runs, not part of the proof.
[docs/emulator.md](docs/emulator.md) covers installation, the design
decisions, the relationship between the two builds' machine code, and the
limitations.
